# Project layout

**Lib and app**: `src/lib.rs` is the lib target, the decode, encode, develop and scoring layer with no egui, winit or wgpu: `coregraphics`, `decode_budget`, `develop`, `export`, `facequality`, `hash`, `image_decode`, `image_encode`, `image_ops`, `immich`, `judge`, `paths`, `quality`, `raw_preview`, `segmentation`, `vision` and `worker_pool`. The app binary and the probes in `src/bin/` and `src/raw/probe.rs` link it. `src/main.rs` imports each of these modules at its root, so app code names them as `crate::develop` like any other module.

**Entry point / event loop**: `src/main.rs` is the app binary's crate root. It owns the winit event loop and `main()`, translating raw window events into calls on `App`. It does not hold app state itself — everything about *what* to show and *how* the loupe is transformed lives in `src/app/`.

**`App` (`src/app/`, `mod.rs` plus 21 domain modules)**: the coordinator that ties together the GPU renderer, the background loader, the ratings/edits catalog, and the egui chrome, plus keyboard bindings. `mod.rs` holds the state shared across areas and the per-frame driving; the rest split by domain (`accessors.rs`, `adjust.rs`, `autotone.rs`, `bulk_delete.rs`, `bursts.rs`, `catalog.rs`, `crop.rs`, `export.rs`, `faces.rs`, `fonts.rs`, `group_compare.rs`, `histogram.rs`, `keys.rs`, `loupe.rs`, `menu.rs` (macOS only), `nav.rs`, `presets.rs`, `score.rs`, `session.rs`, `thumbs.rs`, and `web.rs`, which is `cfg(target_arch = "wasm32")` only). An area with state of its own keeps it in a struct defined in its module, with private fields: `AutoTone`, `CatalogLoad`, `CropState`, `Exports`, `Faces`, `GroupCompare`, `Histogram` and `Web`. Other modules reach that state through the owning module's methods, so a field change stays inside one file. `test_support.rs` holds the folders, Apps and frame-driving harness the `app` tests share. This is the biggest and most central area — read it first when tracing how a keypress or click turns into a state change.

**Rendering split**: two renderers coexist deliberately.
- `src/renderer.rs` + `src/shader.wgsl`: hand-rolled wgpu renderer, draws only the loupe image, confined to a viewport rect. Zoom/pan/rotate update a small uniform, never trigger a re-decode.
- `src/ui/` (12 modules: `mod.rs`, `grid.rs`, `loupe.rs`, `toolbar.rs`, `develop_panel.rs`, `export_panel.rs`, `info_panel.rs`, `modals.rs`, `form.rs`, `tabs.rs`, `theme.rs`, `font_size.rs`): egui chrome (grid, filmstrip, filter bar, rating overlays) built against egui 0.34's `Panel`/`show_inside` API. The Loupe's central region is frameless/transparent so the wgpu image shows through underneath. `ui` reports back the central image rect and any user actions (clicks, slider, filter changes) for `main.rs`/`app` to apply — it doesn't mutate `App` state directly. Every form builds on `form.rs`, and the Forms section of CLAUDE.md has its rules.

**Background decode/loader (`src/loader.rs`)**: a worker thread pool decodes off the UI thread, with two cache tiers sharing one work queue and one results channel — a full-image LRU for the loupe (`request_preview`/`get_preview`/`get_full`) and a larger thumbnail LRU for the grid/filmstrip (`request_thumb`/`get_thumb`, backed by `src/thumbnail.rs`'s on-disk `ThumbCache`); both tiers are drained together once per frame by `poll_all`. Jobs are prioritized (full-image over thumbnail over capture-time metadata reads) with a dedicated worker reservation so a freshly opened image isn't stuck behind a thumbnail flood — see the priority-queue and reservation comments in `loader.rs` before touching scheduling.

**Decode/encode (`src/image_decode.rs` + `src/image_encode.rs`)**: counterpart pipelines with one arm per platform. On macOS both are built on Apple's ImageIO + CoreGraphics (CFURL → CGImageSource/CGImageDestination, drawn through a CGBitmapContext). `src/coregraphics.rs` holds the classic (non-block) CoreGraphics symbol declarations and CFURL/bitmap-context setup shared by both, since `objc2-core-graphics` 0.3 doesn't surface them. `src/thumbnail.rs` mirrors `image_decode.rs` but asks ImageIO for a decode-at-size preview instead of a full decode. Off macOS the same entry points resolve to the `image`, `rawler`, `kamadak-exif` and `mozjpeg-rs` crates in `src/raw/` below. [`ARCHITECTURE.md`](../ARCHITECTURE.md) is the sequencing view of all three targets. This file is the module map.

**RAW and the non-mac decode arm (`src/raw/`, 4 files)**: not a `raw` module. Each file is mounted where it is used, by `#[path]`. `image_decode.rs` mounts `raw/nonmac_decode.rs` with a glob re-export, so on Linux, Windows and wasm32 a call to `image_decode::decode` lands there. `renderer.rs` mounts `raw/render.rs`, the GPU tonemap pipeline for linear-light RAW images. `raw/preview.rs` is the two-tier RAW decode (`Fast` quarter-res binning, `Quality` full PPG demosaic) that the lib mounts as `raw_preview` for the browser's decode workers and the probe. `raw/decode_budget.rs` is mounted by the lib the same way. `raw/probe.rs` is its own `decode_probe` binary, a decode test harness over synthetic DNG fixtures.

**Develop / edits model (`src/develop.rs`)**: `Adjustments` is the single source of truth for non-destructive edits (persisted via serde in the catalog); `GpuAdjust` is its packed `#[repr(C)]` mirror uploaded as a uniform to the shader; `apply_linear` is a CPU mirror of the same tone pipeline used for the live histogram, so the WGSL shader and the histogram never disagree. Tone sliders are −100..=100 (0 = identity), exposure is −5..=5 stops (0 = identity); `Adjustments::default()` is the identity edit.

**Auto Tone (`src/autotone.rs` + `src/app/autotone.rs`)**: two halves with a hard line between them. `src/autotone.rs` is pure analysis — it bins a downscaled linear-light sample by *display* luma, then solves Exposure, Blacks, Whites and Contrast by bisecting against `develop::apply_linear` (or `apply_raw_display` for RAW) rather than guessing constants, so it can never drift out of sync with what the shader draws; Highlights, Shadows and Vibrance stay heuristic because they have no target to solve for. The one invariant to preserve when touching it: each bin stores a representative linear-light *colour* seated on that bin's own display level, not a neutral grey of its linear luma — a grey stand-in does not reproduce a saturated pixel's display luma and silently biases every percentile. Re-sort the representatives by output luma for each candidate adjustment: different colours can exchange brightness order through the pipeline. `src/app/autotone.rs` is the wiring: it sources pixels from whatever is cheapest (the shown photo's existing `hist_sample`, otherwise the 512px thumbnail the grid already caches), writes results through `edits` + the catalog, and runs a selection-wide batch that queues missing thumbnails and is advanced each frame by `poll_auto_tone`. A batch is abandoned on a folder change (`cancel_auto_tone`), because it writes through whichever catalog is active *now* and `Catalog` keys its records by filename alone.

**Pure pixel ops (`src/image_ops.rs`)**: crop/tone/rotate math with no `App` dependency, shared by export (`src/export.rs`), thumbnail baking, and the histogram — this is what guarantees an exported JPEG matches the on-screen edited thumbnail.

**Export (`src/export.rs`)**: exporting bakes edits into a full-resolution decode and writes JPEG via ImageIO — expensive, so it runs on `worker_pool::WorkerPool` rather than the UI thread. That pool is shared with `score.rs` and `facequality.rs`: threads that take jobs from one queue, and a job that panics still reports a result, since every caller counts results to know when its work is done. Workers are handed a fully self-contained `ExportJob` and never touch `App` state, so there's no shared-state coupling to reason about. A job's `ExportDest` is either a collision-free file path or an Immich upload; `immich.rs` is the blocking HTTP client the workers call for the latter, and `secret.rs` keeps its API key in the macOS Keychain. The settings the job is built from come from the inline export form (`ui/export_panel.rs`), which replaces the Develop panel while it is open.

**Catalog / persistence (`src/catalog.rs`)**: ratings + develop edits live in per-photo sidecar files, `<photo's directory>/.lightphotos/<photo filename>.xmp` (the `.xmp` extension is cosmetic — the body is our own JSON, not real Adobe XMP/RDF), so they travel with a folder when it's moved, copied, or shared instead of being orphaned by a single global catalog. `.lightphotos` is created lazily on first write. `Catalog` is scoped to one active directory at a time — `open_dir` (called from `App::seed_mirrors` on every folder/file open, including sidebar subfolder navigation) reloads its in-memory read cache from that directory's sidecars; individual reads/writes still resolve directly from a photo's own path, independent of the active directory. Writes are one-file-per-photo, atomic (temp file + rename), and they leave the frame through the queue in `src/catalog/writeback.rs`, because a single sidecar write costs around 80-120 µs on APFS and rating a 20 000-photo selection inline froze the window for seconds. Originals in photo folders are never touched. An earlier design kept one global catalog (JSON, then SQLite) keyed by absolute path; it was migrated out to sidecars in `016f0af` and the migration code itself was removed in `a3e6dfa`, so nothing in `src/` reads a legacy catalog today.

**Photo groups (`src/groups.rs`)**: a group is two or more photos in one folder that show as one, its representative. Each group is one sidecar, `.lightphotos/groups/<id>.json`, holding `{"v":1,"members":[...],"representative":"..."}`, so a group's members and representative change together in one atomic write instead of across several photo sidecars. `groups.rs` is pure, in the style of `quality.rs`. `Group::new` is its only constructor. It refuses fewer than two distinct members, a representative outside them, or a member name that is not UTF-8, since the sidecar's JSON cannot hold one, and it sorts members by name the way the folder lists them. `Groups` indexes a folder's groups by id and by member, so a photo is in at most one group. Its mutations (`create`, `set_rep`, `dissolve`, `forget`) return the sidecar writes they imply as `GroupWrite`s, and `Groups::apply` is the only thing that changes the index. `Catalog` owns the active folder's `Groups`. `load_sidecars` parses `groups/` in the same background pass as the photo sidecars, into the codec in `src/catalog/group_file.rs`; only bad JSON or an unknown version counts as unreadable. `Catalog::apply_loaded` then reconciles the parsed files against the playlist's images with `Groups::from_loaded`, which drops a member that is not one of them, drops a group left under two members, and gives a photo two sidecars claim to the newest group. A minted id is `g-<ms since the epoch, 12 hex digits>-<6 hex digits>`, so ids order by creation time; any other id, such as the fixture script's `g-fixture00001`, counts as older than every minted one and orders by name among its kind. `create` writes the new group before it shrinks or deletes the groups it took photos from, so a crash between the two still loads with the photos in the new group. Loading never writes. It records every group it repaired or dropped, and the first batch of writes after the load, from any mutation, also rewrites or deletes those files, so a dropped group cannot come back when its missing photo does. `Catalog::apply_group_writes` applies a mutation's writes to memory and queues them on the same writeback queue as photo sidecars. The browser build does the same through the folder's File System Access handle: `web_catalog_fs::load_sidecars` reads `groups/` with the same codec, and the wasm writeback queue sends a group's writes to `write_group` and `delete_group`, which put them in `groups/` rather than beside the photo sidecars.

**Quality score (`src/quality.rs`, `src/judge.rs`, `src/score.rs`, `src/app/score.rs`)**: a 0-100 score per photo, computed only when the user asks (Photo > Score Quality, or the selection bar's Score) for the selection or the Loupe photo, never for a whole folder. `quality.rs` is pure and builds everywhere: `technical` measures rendered pixels (focus per tile against the tile's own contrast, clipped highlights and shadows, mean luma, an Immerkaer noise estimate on the flattest tiles), and `score` multiplies a base by one table of penalty curves (`CURVES`), so tuning happens there. The base is Vision's aesthetics score on macOS 15 and later and a flat 0.5 otherwise, which is why a technical-only score tops out at 50. `judge.rs` turns pixels into a score; on macOS it runs face landmarks and, where the runtime has `VNCalculateImageAestheticsScoresRequest`, the aesthetics request on one `VNImageRequestHandler` built from the same pixels. `score.rs` holds `ScorePool`, two to four low-priority workers apart from the decode pool, and `ScoreJob`, which hands the pool one photo per free worker so nothing queues behind it. Each worker decodes a 1024 px preview, bakes the photo's edits in with `image_ops::bake_edited`, and judges the result. `app/score.rs` stores each result in the photo's sidecar (`ImageRecord::score`) with the edit signature it was measured on, so a later edit shows the score dimmed as stale. The grid draws the number beside the stars, the Loupe's info bar draws it with the penalties on hover, and the toolbar's Sort: Quality orders the grid by it. `src/bin/score_probe.rs` scores a folder and prints the Spearman correlation between score and star rating, for tuning the curves.

**Apple Vision (`src/vision.rs`, `src/facequality.rs`, `src/segmentation.rs`)**: macOS only. `vision.rs` compiles only on macOS, and the non-mac arm of the other two returns `Err` without doing anything. `vision.rs` is the shared plumbing and nothing else. It runs a set of `VNRequest`s on one handler over a file URL or an in-memory `CGImage` and blocks, and `require_class` checks a request class exists before a request newer than macOS 11 is built. Two users sit on top. `facequality.rs` runs face-landmark detection and then scores eye openness with plain geometry, which is what the eyes-closed filter reads. `segmentation.rs` asks for a person mask first and falls back to a general foreground mask, which is what the Loupe's "Show Selection" overlay draws. `facequality.rs` owns a two-worker thread pool (`FacePool`); segmentation spawns one thread per request from `src/app/loupe.rs`. Vision decodes the file itself, at full resolution, so none of this goes through `loader.rs` or its caches.

**macOS integration**: `src/macos_delegate.rs` hooks Finder "open document" events (double-click / "Open With" / `open -a`) by adding an `application:openURLs:` method to winit's own `NSApplicationDelegate` class at runtime via the Objective-C runtime, since winit both requires owning the app delegate and doesn't implement that method itself. It forwards the opened path into the winit event loop via an `EventLoopProxy`. `src/trash.rs` moves files to the macOS Trash via `NSFileManager`.

**Navigation (`src/navigation.rs`)**: given an opened image, lists sibling images in the same directory (sorted) for prev/next stepping.

**Hashing (`src/hash.rs`)**: a minimal dependency-free FNV-1a 64-bit hasher, used because it's stable/deterministic across process runs (unlike `DefaultHasher`) — needed for the on-disk thumbnail cache key and the develop edit signature. It is not a perceptual hash.

**Localization (`src/i18n.rs`)**: every user-facing string, one `Strings` value per language, so a string missing from any language is a compile error. English and Simplified Chinese ship today. Log lines, CLI output and OS error details stay English.

**Browser build (`src/web/`, 8 files)**: not a `web` module either. `src/main.rs` mounts each file at the crate root by `#[path]` under `cfg(target_arch = "wasm32")`, so they are `crate::web_fs` and not `crate::web::web_fs`. `web_fs.rs` picks, lists and reads folders through the File System Access API, standing in for `navigation.rs`. `web_catalog_fs.rs` and `web_thumb_cache.rs` are the File System Access counterparts of the sidecar and thumbnail-cache I/O in `catalog.rs` and `thumbnail.rs`, and both keep the native entry naming, so one folder's cache serves the app and the browser. `web_export_fs.rs` implements `export::ExportFs` over a writable stream. `web_canvas.rs` inserts winit's `<canvas>` into the page. Decoding runs on `loader.rs`'s own worker threads, which on wasm32 are wasm threads over one shared memory (nightly, cross-origin isolated; see CLAUDE.md). A thread cannot open a File System Access handle, so `app/web.rs` reads each file on the main thread and `web_decode.rs` holds the jobs the threads run over those bytes: thumbnail, Loupe and export decodes. `web_exports.rs` keeps each export's destination folder handle on the main thread until its JPEG comes back. `analytics.rs` reports load and decode events to the site.

**Headless driver (`src/drive.rs`)**: `--drive <script>` runs the real `App`, egui frame and renderer with no visible window and no OS input, so a live check can run on a shared desktop and ten can run at once. A script is one step per line, parsed at the command-line boundary into `Step` so a typo fails with its line number before anything runs. Pointer steps are built as winit events and go through `App::window_event`; key steps push the egui events `egui_winit` would and call `App::key_input`, because winit's `KeyEvent` cannot be built outside winit. `idle` pumps `App::pump` until nothing is outstanding, `shot` reads the renderer's offscreen texture back to a PNG, and `state` prints one JSON line. Settings go to a scratch directory for the run (`prefs::override_config_dir`), never the person's own. Native only.

**Small helpers**: `src/paths.rs` normalizes a path into a stable file identity and picks free `<stem>-N.jpg` export names. `src/dialog.rs` is a 14-line wrapper over `rfd`'s native folder picker, not compiled on wasm32, which has its own async picker in `web_fs.rs`. `src/profile.rs` compiles only under the `hotpath` feature. It drives folder listing, then a table of phases covering grid and filmstrip thumbnails, opening a photo, the full-resolution decode, Auto Tone, a batch export, subject selection and the Vision signals, all headlessly, so a profiling run is reproducible rather than dependent on how someone scrolled.
