# Project layout

**Entry point / event loop**: `src/main.rs` is the crate root. It owns the winit event loop and `main()`, translating raw window events into calls on `App`. It does not hold app state itself — everything about *what* to show and *how* the loupe is transformed lives in `src/app/`.

**`App` (`src/app/`, `mod.rs` plus 13 domain modules)**: the coordinator that ties together the GPU renderer, the background loader, the ratings/edits catalog, and the egui chrome, plus keyboard bindings. `mod.rs` holds the state and the per-frame driving; the rest split by domain (`accessors.rs`, `adjust.rs`, `autotone.rs`, `bulk_delete.rs`, `catalog.rs`, `crop.rs`, `export.rs`, `histogram.rs`, `keys.rs`, `loupe.rs`, `nav.rs`, `thumbs.rs`, and `web.rs`, which is `cfg(target_arch = "wasm32")` only). This is the biggest and most central area — read it first when tracing how a keypress or click turns into a state change.

**Rendering split**: two renderers coexist deliberately.
- `src/renderer.rs` + `src/shader.wgsl`: hand-rolled wgpu renderer, draws only the loupe image, confined to a viewport rect. Zoom/pan/rotate update a small uniform, never trigger a re-decode.
- `src/ui/` (7 modules: `mod.rs`, `grid.rs`, `loupe.rs`, `toolbar.rs`, `develop_panel.rs`, `survey.rs`, `modals.rs`): egui chrome (grid, filmstrip, filter bar, rating overlays) built against egui 0.34's `Panel`/`show_inside` API. The Loupe's central region is frameless/transparent so the wgpu image shows through underneath. `ui` reports back the central image rect and any user actions (clicks, slider, filter changes) for `main.rs`/`app` to apply — it doesn't mutate `App` state directly.

**Background decode/loader (`src/loader.rs`)**: a worker thread pool decodes off the UI thread, with two cache tiers sharing one work queue and one results channel — a full-image LRU for the loupe (`request_preview`/`get_preview`/`get_full`) and a larger thumbnail LRU for the grid/filmstrip (`request_thumb`/`get_thumb`, backed by `src/thumbnail.rs`'s on-disk `ThumbCache`); both tiers are drained together once per frame by `poll_all`. Jobs are prioritized (full-image over thumbnail over capture-time metadata reads) with a dedicated worker reservation so a freshly opened image isn't stuck behind a thumbnail flood — see the priority-queue and reservation comments in `loader.rs` before touching scheduling.

**Decode/encode (`src/image_decode.rs` + `src/image_encode.rs`)**: counterpart pipelines with one arm per platform. On macOS both are built on Apple's ImageIO + CoreGraphics (CFURL → CGImageSource/CGImageDestination, drawn through a CGBitmapContext). `src/coregraphics.rs` holds the classic (non-block) CoreGraphics symbol declarations and CFURL/bitmap-context setup shared by both, since `objc2-core-graphics` 0.3 doesn't surface them. `src/thumbnail.rs` mirrors `image_decode.rs` but asks ImageIO for a decode-at-size preview instead of a full decode. Off macOS the same entry points resolve to the `image`, `rawler`, `kamadak-exif` and `mozjpeg-rs` crates in `src/raw/` below. [`ARCHITECTURE.md`](../ARCHITECTURE.md) is the sequencing view of all three targets. This file is the module map.

**RAW and the non-mac decode arm (`src/raw/`, 4 files)**: not a `raw` module. Each file is mounted where it is used, by `#[path]`. `image_decode.rs` mounts `raw/nonmac_decode.rs` with a glob re-export, so on Linux, Windows and wasm32 a call to `image_decode::decode` lands there. `renderer.rs` mounts `raw/render.rs`, the GPU tonemap pipeline for linear-light RAW images. `raw/preview.rs` is the two-tier RAW decode (`Fast` quarter-res binning, `Quality` full PPG demosaic) that the browser's Web Worker pulls in the same way. `raw/probe.rs` is its own `decode_probe` binary, a decode test harness over synthetic DNG fixtures.

**Develop / edits model (`src/develop.rs`)**: `Adjustments` is the single source of truth for non-destructive edits (persisted via serde in the catalog); `GpuAdjust` is its packed `#[repr(C)]` mirror uploaded as a uniform to the shader; `apply_linear` is a CPU mirror of the same tone pipeline used for the live histogram, so the WGSL shader and the histogram never disagree. Tone sliders are −100..=100 (0 = identity), exposure is −5..=5 stops (0 = identity); `Adjustments::default()` is the identity edit.

**Auto Tone (`src/autotone.rs` + `src/app/autotone.rs`)**: two halves with a hard line between them. `src/autotone.rs` is pure analysis — it bins a downscaled linear-light sample by *display* luma, then solves Exposure, Blacks, Whites and Contrast by bisecting against `develop::apply_linear` (or `apply_raw_display` for RAW) rather than guessing constants, so it can never drift out of sync with what the shader draws; Highlights, Shadows and Vibrance stay heuristic because they have no target to solve for. The one invariant to preserve when touching it: each bin stores a representative linear-light *colour* seated on that bin's own display level, not a neutral grey of its linear luma — a grey stand-in does not reproduce a saturated pixel's display luma and silently biases every percentile. Re-sort the representatives by output luma for each candidate adjustment: different colours can exchange brightness order through the pipeline. `src/app/autotone.rs` is the wiring: it sources pixels from whatever is cheapest (the shown photo's existing `hist_sample`, otherwise the 512px thumbnail the grid already caches), writes results through `edits` + the catalog, and runs a selection-wide batch that queues missing thumbnails and is advanced each frame by `poll_auto_tone`. A batch is abandoned on a folder change (`cancel_auto_tone`), because it writes through whichever catalog is active *now* and `Catalog` keys its records by filename alone.

**Pure pixel ops (`src/image_ops.rs`)**: crop/tone/rotate math with no `App` dependency, shared by export (`src/export.rs`), thumbnail baking, and the histogram — this is what guarantees an exported JPEG matches the on-screen edited thumbnail.

**Export (`src/export.rs`)**: exporting bakes edits into a full-resolution decode and writes JPEG via ImageIO — expensive, so it runs on a small worker pool (mirroring `loader.rs`) rather than the UI thread. Workers are handed a fully self-contained `ExportJob` and never touch `App` state, so there's no shared-state coupling to reason about.

**Catalog / persistence (`src/catalog.rs`)**: ratings + develop edits live in per-photo sidecar files, `<photo's directory>/.lightphotos/<photo filename>.xmp` (the `.xmp` extension is cosmetic — the body is our own JSON, not real Adobe XMP/RDF), so they travel with a folder when it's moved, copied, or shared instead of being orphaned by a single global catalog. `.lightphotos` is created lazily on first write. `Catalog` is scoped to one active directory at a time — `open_dir` (called from `App::seed_mirrors` on every folder/file open, including sidebar subfolder navigation) reloads its in-memory read cache from that directory's sidecars; individual reads/writes still resolve directly from a photo's own path, independent of the active directory. Writes are one-file-per-photo, atomic (temp file + rename), and they leave the frame through the queue in `src/catalog/writeback.rs`, because a single sidecar write costs around 80-120 µs on APFS and rating a 20 000-photo selection inline froze the window for seconds. Originals in photo folders are never touched. An earlier design kept one global catalog (JSON, then SQLite) keyed by absolute path; it was migrated out to sidecars in `016f0af` and the migration code itself was removed in `a3e6dfa`, so nothing in `src/` reads a legacy catalog today.

**Best-of-burst (`src/burst.rs` + `src/sharpness.rs`)**: `sharpness.rs` scores focus via variance-of-Laplacian on a downscaled grayscale image (comparable across differing resolutions); `burst.rs` is pure/total logic that, given a burst grouping and scores, decides the best frame per burst and its siblings — deliberately free of UI/filesystem/decode state so it's unit-testable in isolation.

**Duplicate grouping (`src/phash.rs` + `src/duplicates.rs`)**: `phash.rs` is a 64-bit difference hash (dHash) that pulls in no external crate. It shrinks a photo to a 9x8 gray grid and records whether each pixel is darker than its right neighbour, so two similar frames land a few bits apart regardless of size. `duplicates.rs` puts any two photos within `DEFAULT_MAX_DISTANCE` (8 of 64 bits) in one group, and those joins chain, so `a~b` plus `b~c` groups all three even when `a` and `c` are far apart. `refine_by_feature_print` then splits members that Vision judges further from the group anchor than `DEFAULT_MAX_FEATURE_DISTANCE`. Both files are pure and unit-tested in the style of `burst.rs`.

**Apple Vision (`src/vision.rs`, `src/featureprint.rs`, `src/facequality.rs`, `src/segmentation.rs`)**: macOS only. `vision.rs` compiles only on macOS, and the non-mac arm of the other three returns `Err` without doing anything. `vision.rs` is the shared plumbing and nothing else. It runs one `VNRequest` against a file URL and blocks. Keep it free of other crate modules, because `src/bin/face_probe.rs` and `src/bin/seg_probe.rs` include it by `#[path]` and the crate has no lib target. Three users sit on top. `featureprint.rs` computes learned image embeddings and the distance between two of them, which is what refines duplicate groups. `facequality.rs` runs face-landmark detection and then scores eye openness with plain geometry, which is what the eyes-closed filter reads. `segmentation.rs` asks for a person mask first and falls back to a general foreground mask, which is what the Loupe's "Show Selection" overlay draws. The first two own two-worker thread pools (`DistancePool`, `FacePool`); segmentation spawns one thread per request from `src/app/loupe.rs`. Vision decodes the file itself, at full resolution, so none of this goes through `loader.rs` or its caches.

**macOS integration**: `src/macos_delegate.rs` hooks Finder "open document" events (double-click / "Open With" / `open -a`) by adding an `application:openURLs:` method to winit's own `NSApplicationDelegate` class at runtime via the Objective-C runtime, since winit both requires owning the app delegate and doesn't implement that method itself. It forwards the opened path into the winit event loop via an `EventLoopProxy`. `src/trash.rs` moves files to the macOS Trash via `NSFileManager`.

**Navigation (`src/navigation.rs`)**: given an opened image, lists sibling images in the same directory (sorted) for prev/next stepping.

**Hashing (`src/hash.rs`)**: a minimal dependency-free FNV-1a 64-bit hasher, used because it's stable/deterministic across process runs (unlike `DefaultHasher`) — needed for the on-disk thumbnail cache key and the develop edit signature. It is not a perceptual hash. `phash.rs` above is.

**Localization (`src/i18n.rs`)**: every user-facing string, one `Strings` value per language, so a string missing from any language is a compile error. English and Simplified Chinese ship today. Log lines, CLI output and OS error details stay English.

**Browser build (`src/web/`, 7 files)**: not a `web` module either. `src/main.rs` mounts each file at the crate root by `#[path]` under `cfg(target_arch = "wasm32")`, so they are `crate::web_fs` and not `crate::web::web_fs`. `web_fs.rs` picks, lists and reads folders through the File System Access API, standing in for `navigation.rs`. `web_catalog_fs.rs` and `web_thumb_cache.rs` are the File System Access counterparts of the sidecar and thumbnail-cache I/O in `catalog.rs` and `thumbnail.rs`, and both keep the native entry naming, so one folder's cache serves the app and the browser. `web_export_fs.rs` implements `export::ExportFs` over a writable stream. `web_canvas.rs` inserts winit's `<canvas>` into the page. `web_worker_pool.rs` is the main-thread side of a pool of `web_sys::Worker`s, each running the separate `wasm_worker` binary (`src/web/wasm_worker.rs`) in its own wasm memory, which is what avoids needing `SharedArrayBuffer` or nightly Rust.

**Small helpers**: `src/paths.rs` normalizes a path into a stable file identity and picks free `<stem>-N.jpg` export names. `src/dialog.rs` is a 14-line wrapper over `rfd`'s native folder picker, not compiled on wasm32, which has its own async picker in `web_fs.rs`. `src/profile.rs` compiles only under the `hotpath` feature. It drives folder listing, then a table of phases covering grid and filmstrip thumbnails, opening a photo, the full-resolution decode, Auto Tone, a batch export and the Vision signals, all headlessly, so a profiling run is reproducible rather than dependent on how someone scrolled.
