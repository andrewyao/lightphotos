# Plan C — Duplicate grouping + Survey Mode

See `00-overview.md` for shared context, architecture patterns, and execution order (this plan runs second, after Plan B).

**What**: Groups visually-similar frames regardless of capture-time gap (today's `burst.rs` only groups by a 2-second time window, missing similar shots taken further apart or re-imported from multiple cards/cameras) — Aftershoot's "Duplicate Grouping With Intent". Paired with **Survey Mode**: a side-by-side review UI for one group, plus a one-click "keep best, rate rest low" action, and a general **"Delete all Rejects" bulk action** (trash everything currently rated 1-2, reusing the existing rating convention and `trash.rs`'s move-to-Trash — no new catalog state needed for this part).

**Grouping signal — two-tier, dHash first + Vision `VNFeaturePrintObservation` as a stronger second pass**: start with dHash (cheap, dependency-free, always available) to get a coarse candidate grouping, since it's enough to catch most near-duplicates from thumbnails alone. Then, for photos dHash marks as candidates (or borderline cases near the distance threshold), compute a `VNFeaturePrintObservation` (Apple's built-in learned image-similarity embedding, via `VNGenerateImageFeaturePrintRequest`) and compare via its native distance function — this is real learned similarity, not just pixel-gradient hashing, so it's meaningfully better at Aftershoot's exact claim: telling a true duplicate (same framing, same moment) apart from a creative variation (different pose/expression, similar framing). Two-tier keeps the common case cheap and only pays the heavier Vision cost where it matters.

**Implementation**:
- New `src/phash.rs` (pure, mirrors `sharpness.rs`'s style): `dhash(rgba: &[u8], width: u32, height: u32) -> u64` (resize to 9×8 luma via a shared downscale helper — factor this out of `sharpness.rs` into `image_ops.rs` if not already shared — then row-wise gradient thresholding into a 64-bit hash), `hamming(a: u64, b: u64) -> u32`.
- New `src/featureprint.rs` (Vision FFI glue, same pattern/dependency as Plan D's `facequality.rs` — if both plans land, factor the shared `VNImageRequestHandler` setup into one place rather than duplicating it): wraps `VNGenerateImageFeaturePrintRequest` → `VNFeaturePrintObservation`, exposes `fn feature_distance(a: &FeaturePrint, b: &FeaturePrint) -> f32` (thin wrapper over the observation's own `computeDistance`).
- New `src/duplicates.rs` (pure, mirrors `burst.rs`): `group_by_hash(hashes: &[Option<u64>], max_distance: u32) -> Vec<u32>`, analogous to `group_by_time`, for the first dHash pass. A default fixed distance threshold (e.g. Hamming ≤ 8 of 64 bits), no UI knob initially — consistent with how `BURST_GAP` is a fixed constant today. Then a second refinement pass merges/splits dHash-candidate groups using feature-print distance (fixed threshold again, no UI knob initially).
- `app.rs`: `phashes: HashMap<PathBuf, u64>` and `feature_prints: HashMap<PathBuf, FeaturePrint>` caches filled off thumbnail arrival (same lazy pattern as `sharpness`) — feature-print computation only triggered for photos already in a dHash candidate group, not the whole folder, to bound cost. `dup_marks: Vec<Option<DuplicateMark>>` parallel to `burst_marks`, recomputed the same way `recompute_burst_marks` is. dHash pass runs over the whole folder (not just burst members already known) — gate behind a toggle mirroring `bursts_on` so cost is opt-in.
- `ui.rs`: a Survey Mode (new `ViewMode::Survey` or a modal overlay opened from a duplicate-group badge in Grid) showing every frame in one group at larger size, with live rating hotkeys still active, plus a one-click action that sets the best-scoring frame's rating up and drops the rest to a reject-range rating (1-2) in one call (the "Spray Can" analog). Grid badge: extend the existing burst-badge corner-drawing block in `draw_grid` to also flag duplicate-group membership (a photo can be in both a time-burst and a content-duplicate group — these are separate underlying computations, unified only at the UI badge layer).
- "Delete all Rejects": a toolbar button/shortcut, `UiAction::DeleteRejects` (or reuse `BulkKind` machinery over "everything rated 1-2 in the current filter"), calls `trash.rs`'s existing move-to-Trash for each. No new catalog column.

**Effort/Priority**: Medium. The dHash pure modules are small and cheap to write/test; the `VNFeaturePrintObservation` refinement pass adds a real Vision-framework dependency (shared setup with Plan D if both land) but only runs on a small candidate subset, so its cost is bounded. Most UI effort is the Survey Mode view and the whole-folder background dHash scoring pass (vs. today's burst-only scoring).

**Critical files**: `src/phash.rs` (new), `src/featureprint.rs` (new), `src/duplicates.rs` (new), `src/app.rs`, `src/ui.rs`, `src/image_ops.rs` (shared downscale helper), `src/trash.rs` (reused, not modified)

**Verification**: unit tests in `phash.rs`/`duplicates.rs` with synthetic image buffers (near-identical vs clearly different) confirming correct hash distance and grouping; a small standalone check of `featureprint.rs` against a couple of real photo pairs (one true duplicate, one similar-but-different) confirming its distance ordering matches expectation before wiring into the grouping pass. End-to-end: `cargo build --release`, run against a real folder containing known near-duplicate shots taken seconds-to-minutes apart plus a couple of similar-but-distinct shots, confirm dHash+feature-print correctly separates them, Survey Mode shows groups side-by-side, "keep best" and "Delete all Rejects" behave as expected.
