Scripted checks in `$TMPDIR` (read-only on the repo):
- key sets and order per locale (596 keys each);
- placeholder tokens (`{name}`, `{n}`, `{version}`, `{size}`, ...);
- numeric literals;
- sentence counts against English;
- strings identical to English;
- help-table key columns;
- unused `Strings` fields;
- a broader hard-coded-English scan of `src/ui`, `src/app` and `src/shell`.

## Summary
The module is in good shape structurally. Every language is one `Strings` value, so a missing key is a compile error. All six translations have the same 596 keys in the same order. Every runtime-substituted placeholder (`{version}`, `{size}`, `{why}`, `{feature}`, `{file}`, `{where}`, `{button}`, `{done}`, `{of}`, `{failed}`) survives in every locale. There are no unused fields, no empty strings, and no panicking paths in non-test code apart from one bounded index. The locale-tag parser is well tested.

The real problems are at the edges:
1. Windows never detects the OS language.
2. Two strings still print `Cmd+Shift+E` on Windows, Linux and non-Mac browsers.
3. 23 help-overlay rows are English in de/fr/ja/ko.
4. The guard test that is supposed to catch hard-coded English covers about a third of the UI/app files.

Findings: 0 Critical, 0 High, 3 Medium, 8 Low, 3 Info.

## Findings

### [I18N-01] No OS-language detection on Windows; POSIX `LC_ALL=C` is ignored — Severity: Medium — Confidence: High
- Location: `src/i18n.rs:192-199` (`system_tags`, non-mac), `src/i18n.rs:139-145` (`init`), doc at `:135-138`.
- Evidence: the non-mac, non-wasm branch reads only `LC_ALL`, `LC_MESSAGES` and `LANG`. `Cargo.toml` has no locale crate, and `windows-sys` is enabled only for `Win32_System_Console` and `Win32_System_Threading`. `init` documents "the OS or browser language".
- Impact:
  - On Windows those variables are normally unset. Unless the user has picked a language in Settings, the app always starts in English, even on a Japanese or German system.
  - The `find_map` in `init` skips tags that fail to parse. With `LC_ALL=C` or `POSIX` (common in CI and containers) and `LANG=de_DE.UTF-8`, it falls through to German although POSIX says `LC_ALL` overrides everything.
  - The GNU `LANGUAGE` priority list is also ignored. The effect is small.
- Suggested fix:
  - On Windows, call `GetUserPreferredUILanguages` or `GetUserDefaultLocaleName` (add `Win32_Globalization` to `windows-sys`) and feed the tags to `from_tag`.
  - On POSIX, take the first non-empty of `LC_ALL`, `LC_MESSAGES`, `LANG` and stop there. Treat `C`/`POSIX` as English. Optionally honour `LANGUAGE` first.
  - Add a unit test for the precedence rule by making `system_tags` take an env-lookup closure.

### [I18N-02] `Cmd+` shortcuts in two strings bypass `i18n::keys()`, so Windows/Linux/non-Mac browsers see "Cmd" — Severity: Medium — Confidence: High
- Location:
  - `src/i18n/en.rs:248` (`export_jpg_tip` "(Cmd+Shift+E)") and its seven translations. Display sites: `src/ui/toolbar.rs:745`, `src/ui/toolbar.rs:1009`, and the rail tip at `src/ui/develop_panel.rs:73`, drawn at `:141-142`. None calls `keys()`.
  - `src/i18n/en.rs:133` (Export tour step "Press Cmd+Shift+E") and its translations, drawn by `src/ui/tour.rs:143` (`ui.label(body)`) without `keys()`.
- Evidence: `keys()` (`i18n.rs:229`) exists precisely to rewrite "Cmd+" to "Ctrl+" at draw time. The other nine fields containing `Cmd+` (`add_folder_tip`, `open_folder_tip`, `apply_settings_tip`, `auto_tone_tip`, `copy_settings_choose_tip`, `settings_tip`, `slideshow_play`, the help key column, and so on) all go through it. These two do not.
- Impact: on Windows and Linux, and in a browser on a non-Mac, the Export button's hover text, the Export rail hover text and the first-run tour all tell the user to press a key that does not exist.
- Suggested fix:
  - Wrap the three call sites in `keys()` and the tour body (`tour.rs:143`) too.
  - Better: make it impossible to forget. Add a test that scans every `Strings` field of every catalog containing `Cmd+` and fails unless the field is on an allow-list of fields known to be wrapped. Or give these fields a distinct type (`KeyedStr`) whose only accessor applies `keys()`.

### [I18N-03] 23 rows of the shortcut overlay are English in German, French, Japanese and Korean — Severity: Medium — Confidence: High
- Location: the key column of `help` in `de.rs:271,305-307,332-333,336-340,358,372,380-383,400-406`. The same rows are English in `fr.rs`, `ja.rs` and `ko.rs`. Examples: "Enter or Space", "Shift+Click", "Cmd+Click", "Shift+arrows", "Space or Z", "Cmd++ or Cmd+=", "Scroll", "Drag", "Space+Drag", "Double-click slider", "Enter or R", "Click or drag the photo", "Shift+scroll on the area", "Drag a tile", "Cmd+Click / Shift+Click a tile".
- Evidence: a script over the `help` blocks finds 23 English-word key cells in each of de, fr, ja and ko, and 0 in zh_hans and zh_hant, which translate them ("Enter 或 Space", "双击滑块", "点击或拖动照片").
- Impact: the key column is a mix of key names (fine to leave) and prose ("or", "Drag a tile", "Click or drag the photo", "Double-click slider") that is English next to a localized description. Users of four of the seven languages see half-English help.
- Suggested fix: translate the prose cells as zh already does, keeping literal key tokens ("Enter", "Space", "Shift"). `help_tables_have_the_same_shape` only checks row counts. Add a test that, for non-English catalogs, fails if a key cell contains an English connective such as ` or `, `Click`, `Drag`, `Scroll` or `slider`.

### [I18N-04] Several CJK translations silently drop a sentence or clause — Severity: Low — Confidence: High
- Location:
  - `comfy_models_hint`: `ja.rs:852`, `ko.rs:836`, `zh_hans.rs:828`, `zh_hant.rs:835`.
  - `zh_hans.rs:791` (`brush_stroke_limit`).
  - `zh_hans.rs:881` (`folder_cant_lock`).
  - `ja.rs:761`/`ko.rs:745` (`import_gps_tracks_tip`, one fewer sentence; probably merged).
- Evidence:
  - English: "ComfyUI's models folder. With none chosen, LightPhotos uses the one ComfyUI Desktop is set to." Ja/ko/zh say only "ComfyUI's models folder."
  - The English `brush_stroke_limit` ends "...; + Brush starts another"; zh_hans omits that clause.
  - English `folder_cant_lock` says "It may be read-only or need permission"; zh_hans omits it.
- Impact: CJK users of the new ComfyUI settings are never told that an empty models folder is acceptable (the fallback behaviour added in commit 53948c5), and lose the actionable hint on read-only folders.
- Suggested fix: restore the omitted sentences. A sentence-count comparison against `en.rs` is a cheap lint (the script used for this review found the above in seconds).

### [I18N-05] The "no hard-coded English" guard test covers about a third of the UI/app files — Severity: Low — Confidence: High
- Location: `src/i18n.rs:1485-1526` (`ui_text_goes_through_the_catalog`), sink list `:1432-1447`.
- Evidence:
  - The test `include_str!`s 23 files. `src/ui`, `src/app` and `src/shell` hold about 75 non-test files.
  - Not scanned: `ui/export_panel.rs`, `ui/form.rs`, `ui/home.rs`, `ui/photo_menu.rs`, `ui/tour.rs`, `ui/mask_overlay.rs`, `app/bulk_delete.rs`, `app/catalog.rs`, `app/comfy.rs`, `app/commands.rs`, `app/geotag.rs`, `app/generative.rs`, `app/group_compare.rs`, `app/masks.rs`, `app/optics.rs`, `app/score.rs`, `app/slideshow.rs`, `shell/menu.rs`, among others.
  - The sink list lacks `Label::new(`, `.hint_text(`, `.checkbox(`, `.radio(`, `.small(`, `add_filter(` and `Window::new(`.
  - It also cannot see a literal bound to a variable first.
- Impact: I re-ran an extended scan (more sinks, all files) and found no current bypass in widgets. So today this is latent, but the one mechanism that enforces the docs/UI.md rule would not catch a new `ui.label("...")` in `export_panel.rs`.
- Suggested fix: walk `src/ui`, `src/app` and `src/shell` with `std::fs::read_dir` from `CARGO_MANIFEST_DIR` inside the test, so new files are included automatically. Add the missing sinks. Keep an explicit allow-list for the few legitimate English literals.

### [I18N-06] English app-authored sentences reach the UI through localized wrappers — Severity: Low — Confidence: Medium
- Location:
  - Generative fill failures: `src/app/generative.rs:101`, `:206`; `src/develop/fill_request.rs:165,168,187,234,281,289,293` (e.g. "the photo has not finished loading; try again in a moment"); `src/comfy/client.rs:99,108,242,261,302,494`; `src/comfy/workflow.rs:79-150`. These become `{why}` in `fill_partial`/`model_failed` or go straight to `set_status` at `generative.rs:247,482,568,697`.
  - Geotag: `src/app/geotag.rs:549` passes the English "the run stopped" into the localized `geotag_read_failed`.
  - `App::run_ui` (`src/app/commands.rs:33-37`) shows `CommandError::to_string()` for keyboard and menu commands, for example `"nothing is copied; run settings.copy first"` (`commands.rs:68`) and the `settings.copy` multi-selection message (`:393`). These are English text that names internal command ids.
- Evidence: CLAUDE.md and the module doc say only "Log lines, CLI output, and OS error details stay English". These are app-authored sentences, not OS details. `generative.rs` already localizes one sentinel (`LOST` becomes `comfy_lost` in `worded`), and the others compare errors by string equality (`STOPPED`, `LOST`).
- Impact: in a non-English UI the ComfyUI failure toast, which the user must act on, reads half English. The `run_ui` cases are mostly guarded by disabled menu items and buttons, so they are rarely reachable.
- Suggested fix: carry a typed error (enum) from `comfy`/`fill_request` to the app and localize at the boundary. This also removes the string-equality sentinels. For `run_ui`, map `Failed` for UI-initiated commands to localized strings, or drop the toast for guarded commands.

### [I18N-07] Placeholder and fn-string coverage in tests is thin — Severity: Low — Confidence: High
- Location: `src/i18n.rs:1639-1672` (`count_messages_show_their_numbers`).
- Evidence:
  - The test checks that 17 of the roughly 50 `fn` strings contain their numbers. `fn(&str, ...)` strings such as `deleted_partial`, `uploaded_partial`, `lr_import_status`, `geotag_done` and `capture_date` (only partly, in another test) are not exercised across languages.
  - Static strings with runtime `{token}` substitution (`update_tip`, `model_download`, `model_failed`, `comfy_blocked_*`, `comfy_not_running`, `comfy_lost`, `fill_generating`, `fill_partial`) have no test at all. If a translator mistypes `{where}` as `{Where}`, the user sees a literal brace token.
- Impact: today all six locales are correct (my script confirms it), but nothing prevents regression.
- Suggested fix: one test per token string asserting `contains("{token}")` in every catalog, or have the call sites go through a helper that debug-asserts the token was replaced.

### [I18N-08] Fonts ignore the UI language (Han unification) and the CJK coverage test only checks Han, kana and Hangul — Severity: Low — Confidence: Medium
- Location: `src/app/fonts.rs:20-90` (no use of `Lang`); `src/i18n.rs:1384-1427`.
- Evidence:
  - Off macOS the stack is egui builtins, then a system Chinese face (`sans-serif:lang=zh-cn`), then the bundled Noto Sans SC subset, then the KR subset, for every language. Japanese kanji and Traditional Chinese therefore draw with Simplified-Chinese glyph forms (the well-known Han-unification differences, for example 直, 骨, 角).
  - The coverage test maps only U+2E80-9FFF, U+FF00-FFEF and Hangul. It does not check symbols the catalogs use everywhere: ▸ (U+25B8, in the `comfy_blocked_*` strings), ★/☆, the curly quotes ‘ ’ used in `ko.rs:824,844-846`, – — … ·.
- Impact:
  - Typographic nit for ja and zh-Hant users.
  - A missing-glyph box for a symbol is possible but I could not confirm it. egui's bundled symbol fonts may cover them.
- Suggested fix: choose the leading CJK face from `lang()` where the platform offers per-language faces. Extend the coverage test to all non-ASCII characters in the catalogs against the final font stack.

### [I18N-09] macOS menu bar is built before `i18n::init()` — Severity: Low — Confidence: High
- Location: `src/main.rs:767` (`shell::menu::install`) then `:772` (`i18n::init()`); `src/shell/menu.rs:449-452`, `:459-463`.
- Evidence: `install` builds `build(i18n::lang())` while `LANG` still holds its default (English). `refresh` (`main.rs:418`) rebuilds when `current.lang != i18n::lang()`.
- Impact: for non-English users the menu is built twice and shows English until the first `refresh`. This is harmless because of the self-correction, but wasteful and order-dependent.
- Suggested fix: call `i18n::init()` before `install`. The wasm `main` and `--drive` already do it early.

### [I18N-10] Indexing in `Strings::band` and `tour_steps`, tied by hand-matched array lengths — Severity: Low — Confidence: High
- Location: `src/i18n.rs:1199-1201` (`self.bands[band as usize]`), `bands: [&str; 8]` at `:632`; `tour_steps: [(..); 9]` at `:347` used as `t.tour_steps[index]` in `src/ui/tour.rs:135`, with `TourStep::ALL: [TourStep; 9]`.
- Evidence: CLAUDE.md forbids `[i]` in non-test code. `Band` has exactly 8 variants today and `TourStep::ALL` has 9, so there is no current panic. But the two literals are independent: adding a ninth `Band` or `TourStep` compiles and panics at the first draw.
- Suggested fix: `self.bands.get(band as usize).copied().unwrap_or("")`, or a `match` on `Band` as `Strings::zone` already does. Use `.get(index)` in `tour.rs`. Or add a const assertion tying the array lengths to the enums.

### [I18N-11] Terminology and register drift inside single catalogs — Severity: Low — Confidence: Medium
- zh_hans:
  - Loupe is "放大视图" in the tour (`zh_hans.rs:117,136`) but "单张视图" in the menu and Open item (`:182,937`).
  - Rating is "评分" almost everywhere but "评级" at `:226,227,338`.
  - Click is "点按" in some rows and "点击" in others (`:300-301` vs `:372-375`).
  - Drag is "拖移" in the zoom section and "拖动" in the brush sections.
  - ASCII colon and comma where full-width is used elsewhere: `:338`, `:519`.
- zh_hant: "模型檔案夾" at `zh_hant.rs:833,835,837,844` while the rest of the file (and Taiwan usage) uses "資料夾". "評級" at `:341` vs "評等" elsewhere. "版權" vs Taiwan's "著作權" (`:679`).
- ko: the GPS block (`ko.rs:745,751,759,767,769,777-783`) uses formal "-습니다" while the other ~130 sentences use "-어요/-해요".
- fr: one typographic apostrophe (`fr.rs:24`) among straight ones everywhere else.
- ja: `ja.rs:345` uses ASCII parentheses without a space in a full-width context; `geotag_read_failed` and `geotag_file_skipped` use ": " where the rest of the file uses "：".
- de: `delete_group_prompt` for one photo says "enthält 1 Foto ... bleiben sie ... erhalten" (`de.rs:476`).
- Impact: polish only. Suggested fix: a native-speaker pass over those lines.

### [I18N-12] Limits are duplicated as literals in the strings — Severity: Info — Confidence: High
- Location: all catalogs: `touch_up_limit` (64), `mask_limit` (16), `brush_point_limit` (8,000), `brush_stroke_limit` (512), `fill_limit` (16), `compare_too_many` / `view_compare_needs_group` / help row "2 to 6".
- Evidence: they currently match `MAX_TOUCHUPS`, `MAX_MASKS`, `MAX_BRUSH_POINTS`, `MAX_STROKES_PER_MASK`, `MAX_FILLS` and `COMPARE_SELECTION_MAX`.
- Impact: none today. Changing a constant leaves seven stale strings.
- Suggested fix: add a test that formats each constant and asserts every catalog's string contains it.

### [I18N-13] No way to force the language for `--drive`/headless runs — Severity: Low — Confidence: Medium
- Location: `src/shell/drive.rs:515-528`, `src/i18n.rs:139-145`.
- Evidence: `--drive` isolates prefs to a temp dir, but `i18n::init()` still reads `NSLocale`/`LANG`, so screenshots and `state` text depend on the host language. There is no `--lang` flag or `?lang=` analogue for native.
- Impact: drive scripts that match on text (or screenshot baselines) behave differently on a German or Japanese Mac.
- Suggested fix: accept a `--lang` option, or default drive runs to English unless asked.

### [I18N-14] Plural handling is ad hoc, and some doc comments are stale — Severity: Info — Confidence: High
- Plural handling:
  - English hedges with "photo(s)". `n_of_m_photos` gives "1 / 1 photos" (English and German; French handles the plural).
  - German and French carry per-string plural logic; ja/ko/zh need none.
  - No shared plural helper exists, so each new count message re-decides.
- Doc comments:
  - `i18n.rs:504-505`: "(preset name, photo count)" above `confirm_auto_tone: fn(usize)`.
  - `i18n.rs:1021-1022`: two stacked doc comments above `view_compare` (the first describes an icon that no longer exists).
  - `i18n.rs:678`: an empty "// Window titles." section.
- Suggested fix: tidy comments. Consider a tiny `plural(n, one, other)` helper.

## Test coverage assessment
Good:
- `locale_tags_map_to_languages` is thorough (Hans/Hant/regions/POSIX forms/empties).
- Round-trip of stored codes, the legacy `zh` code, URL query parsing, and index-matches-`ALL` all have tests.
- `capture_dates_follow_each_language`.
- Help tables have the same row counts across languages.
- English help lists every key `handle_key` binds.
- The CJK font coverage test fails with the exact subset script to run.

Weak or missing:
- Detection precedence (`system_tags`) is untested; it reads global env and cannot be unit tested as written (I18N-01).
- `init()` ordering and the query > saved > system precedence are untested.
- No placeholder-token tests (I18N-07), no `Cmd+` routing test (I18N-02), no key-cell language test (I18N-03), no sentence-parity lint (I18N-04).
- The hard-coded English scan has incomplete file and sink coverage (I18N-05).
- `lang()` falls back to `En` on an out-of-range atomic; this is unreachable.

## Things done well / verified-safe areas
- 596 keys in identical order in all seven catalogs; no duplicates, no empties, no dead `Strings` fields (verified by script).
- All runtime `{token}` placeholders and all numeric literals match English in every locale (the differences my diff script flagged were only `\u{...}` escapes and plural logic).
- `Lang::from_tag`: robust against empty and hostile input (no indexing or slicing); `lang_from_query` is safe on arbitrary URLs. The enum-to-`u8` store is checked by `language_index_matches_the_all_table`.
- `capture_date` closures use `.get()`, `wrapping_sub` and no unchecked subtraction (`hour - 12` only on 13+). They are panic-free for any input.
- Prefs write failure on `choose()` is logged, not surfaced, with a reasonable rationale.
- Per-platform wording (`WEB`, `RAW_SETTING`, `SUBJECT_KEYS`, Keychain vs file) is handled consistently across all seven languages.
- The Chinese catalogs correctly keep Simplified vs Traditional vocabulary (拷贝/拷貝, 堆叠/堆疊, 废纸篓/垃圾桶).

## Open questions for maintainers
1. Is Windows locale detection intentionally deferred? The `init` doc claims "OS or browser language".
2. Are the English key-column cells in de/fr/ja/ko deliberate (as in "keep key names in English")? If so, the prose cells ("or", "Drag a tile", "Double-click slider") still look unintended given zh translates them.
3. Is the full-width/ASCII punctuation mix in the CJK files intended to follow each platform's conventions (macOS Japanese uses full-width "："; the file mixes both)?
4. Should app-authored error sentences from `comfy`/`develop::fill_request` be localized, or does "OS error details stay English" extend to them?
5. Do ▸ (U+25B8) and the curly quotes render in the bundled egui fonts on Windows and Linux? Nothing tests them.
